# CVE-2026-109618 / 109619 — PHP2Shell — Hunting Guidance

**Date:** 2026-10-22 | **CTI POC:** Austin Mundy

---

## What's Going On

Use-after-free in PHP's session upload progress handler (all versions back to 5.4). Unauthenticated RCE via a crafted multipart POST with a `PHP_SESSION_UPLOAD_PROGRESS` field — no login, no file upload page needed, just a reachable `.php` endpoint. CVSS 9.2. Pre-disclosure exploitation confirmed by AWS on Oct 17, four days before public disclosure. WordPress, Drupal, and Joomla confirmed exploitable pre-auth (Wiz). Memory disclosure (passwords, tokens, API keys) possible even without full RCE.

Fixed versions: 8.2.35, 8.3.36, 8.4.27, 8.5.12. Everything below those, and anything ≤ 8.1, is vulnerable and end-of-life.

EPA has **141 hosts with PHP** (5.x–8.x), 41 actively running. None flagged internet-facing in Defender, but Defender doesn't cover every Linux server — not all PHP hosts may have MDE installed.

**Defender Advanced Hunting queries have been provided separately.** This document covers what to look for from a CTI/hunting perspective, focused on network and log-level indicators.

## Hunt 2 — Scanner Fingerprints in Web/Proxy Logs

Active scanning for PHP2Shell uses distinctive user-agents and request paths. Look for these in any web server access logs or proxy logs that are forwarded to Splunk.

**User-agents to look for:**
- `php2shell-scan/109618`
- `php2shell-scan/1.3 (eigen-oppervlak controle; CVE-2026-109618/109619)`
- `php2shell-verify/1.0`
- `Mozilla/5.0 (php2shell-poc)`
- Empty / missing user-agent with a 13-byte POST body

**Request paths associated with scanning:**
- `/phpinfo.php`, `/info.php`, `/php.php`, `/pi.php`, `/test.php`, `/i.php`
- `/vuln.php`, `/download.php?file=php://filter/...`
- `/php2shell-probe-<random>.php` and `.txt` (scanner drops these to verify write access)

**What matters:** Any POST request from the IOC IPs or with these user-agents hitting a `.php` endpoint. The exploit doesn't require a file upload page — any reachable PHP endpoint works. If web server access logs are in Splunk, look for these patterns against PHP hosts.

```spl
index=epa_* ("php2shell" OR "p2s.txt" OR "php2shell-probe" OR "eigen-oppervlak")
| table _time host src_ip dest_ip url uri_path http_user_agent http_method status
```

## Hunt 3 — PHP Error Log Signatures (Arm & Fire)

The exploit works in two stages that leave specific signatures in PHP-FPM and Apache error logs:

**Arm stage** — The attacker sends oversized session data that triggers a fatal memory error. The distinctive signature is a memory exhaustion error with the location reported as `"in Unknown on line 0"` — normal PHP OOM errors reference a real file and line number; this one doesn't because it happens inside the session handler before any script runs.

**Fire stage** — The second request triggers the use-after-free, causing the PHP-FPM worker to segfault (signal 11 / SIGSEGV). A `"Failed to decode session object"` error may also appear as the corrupted session is cleaned up.

**If PHP-FPM or Apache error logs are forwarded to Splunk:**
```spl
index=epa_* (source="*/php-fpm/*" OR source="*/httpd/error_log*")
  ( ("Allowed memory size" "in Unknown on line 0")
    OR "exited on signal 11" OR "SIGSEGV"
    OR "Failed to decode session object" )
| stats count min(_time) max(_time) by host source
```

**Important:** If this returns nothing, confirm these log sources are actually ingested — empty results may mean the logs aren't forwarded to Splunk, not that the servers are clean.

## Hunt 4 — Filesystem and Session Artifacts

If a host was exploited, there are specific artifacts that would be on disk. This is for awareness — server teams or IR with host access would need to check these:

- **Known exploit session file:** `sess_xqsuvwz3n97wu8j3emz1axuo5y` in the PHP session directory (typically `/var/lib/php/sessions/` or `/tmp/`)
- **Scanner probe files:** `p2s.txt` or files matching `php2shell-probe-*` in web-accessible directories
- **Webshell indicators:** The observed payload writes `<?php echo 'PWNED::'; system($_GET['c']); ?>` — any recently created `.php` file in a web root containing `system($_GET`, `passthru($_`, `shell_exec($_`, or the string `PWNED::` is suspicious
- **Oversized session files:** The arm stage creates abnormally large PHP session files — recently created sessions that are significantly larger than normal baseline warrant a look
- **Multipart boundary string:** `------p2s9rdme2st6guc9g0rafic` in any logged request body
